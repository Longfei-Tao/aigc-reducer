# 论文降 AIGC 率

输入一篇论文 Word + 一份 AIGC 检测报告 → 输出「文字被改写、样式原样保留」的新文档，外加逐段对照表和自检报告。

## 硬边界（先读这段）

1. **只改表达层。** 数字、百分比、年份、结论方向、引用标记 `[1]`、图表编号、公式、表格内容，一律不动。
2. **不承诺分数。** 检测器模型持续迭代，本技能保证「严格按指令改到位」，不保证「降到某个百分比」。交付时必须提醒用户拿回原平台复检。
3. **原文件不动。** 永远输出新文件名，绝不覆盖源文件。
4. **指令不可改。** 见下一节。

## 一、指令的唯一来源

`references/prompt.md` 是用户验证过的改写指令，**这是本技能的核心，等价于用户的原始手工作业**。

每改写一批之前，必须：

1. 用 Read 完整读取 `references/prompt.md`
2. 取第一个 `---` 分隔线之后的全部内容（到文件末尾，含「修改段落:」）
3. 在「修改段落:」之后直接拼上待改段落原文

即每批请求等价于用户手工在对话框里发的：

```
指令:1. 在不大幅改动原文总字数的情况下，只调整语序……
2. 弱化专业感……
3. 弱化语句精炼度……
4. 减少句号使用，多用逗号、分号衔接……
5. 打乱句子原有结构……
修改段落:
<该批段落原文，段落之间空一行>
```

**明令禁止：**

- 凭记忆复述指令，或用「那个降 AI 的提示词」代替实际读取
- 对指令做概括、精简、润色、补充
- 自行追加反向约束（如「同时保持学术严谨性」「不要过于口语」）
- 「优化」指令让它更清晰——**它不需要被优化**

这套拼接已由 `batch --prompt references/prompt.md` 自动完成（见 Step 4），输出文本与手工发送完全等价。**优先用它**：手工抄指令容易漏字，手工抄段落 id 容易错位。

## 二、指令条款的执行口径

以下口径仅用于消解条款之间的冲突，**优先级低于 prompt.md 原文**，冲突时以原文为准。

| 原文条款 | 落地口径 |
|---|---|
| ①「不大幅改动总字数」 | 单段字数变化 ≤ ±15%，全篇 ≤ ±10% |
| ①「补充无主语句的主语」 | 仅在上下文能明确推断时补（本文/本研究/该实验/笔者）；推断不出就保留原状，不要硬造主语 |
| ④「减少句号」+「长句拆短句」 | 两条不矛盾：把长复句拆成若干**短分句，用逗号、分号串联**（一逗到底的流水句），不是切成多个带句号的短句。量化目标：句号减少 20%–60%，逗号增加 |
| ②「平实普通」 vs ⑤「删口水话」 | 平实 = 朴素书面语（「比较简单」「不太好做」）→ 保留；口水话（「说白了」「这东西」「你懂的」）→ 删除 |
| ⑤「打乱结构」 vs「核心表意不变」 | 可换：语序、主被动、把字句、同义词、句式长短。不可换：数字、年份、专有名词、术语所指、引用编号、肯定/否定方向 |

## 三、输入检查

开工前确认两样东西：

| 必需 | 判断 | 缺失时 |
|---|---|---|
| 论文 docx | 扩展名 `.docx`。`.doc` 或 PDF 不行 | 请用户用 Word「另存为」成 .docx |
| 检测报告 | PDF / 图片截图 / 网页导出文本 / 用户口述章节 | 问一句「是整篇都改，还是只改某几节」 |

## 四、流程（六步）

### Step 1 拆文档

```bash
python "<技能目录>/scripts/docx_tool.py" split "论文.docx" -o work/blocks.json --batch-chars 1200
```

看输出摘要确认三件事：可改写字数、表格数量（表格不参与改写）、分批数。

同时读 `work/blocks.json` 里的 `sections` 数组——它是章节树，每项含标题、段落 id 列表、字数，Step 2 定位靠它。

### Step 2 定位高危章节

读检测报告，抽出「章节标题 + 疑似度」，逐条与 `sections[].heading` 比对。比对规则见 `references/report-parsing.md`。

产出待改清单：

| 章节 | 报告疑似度 | 段落 id | 字数 |
|---|---|---|---|
| 3.2 研究方法 | 78% | 45–58 | 1420 |

### Step 3 让用户确认

把清单以表格形式给用户，问：全改 / 只改 ≥X% / 增删某节。

**不要跳过这一步。** 改错章节的返工成本远高于问一句。

### Step 4 分批改写

对每一批：

1. **用 `batch` 取本批请求文本**（不要手抄段落）：

```bash
python "<技能目录>/scripts/docx_tool.py" batch work/blocks.json --id 3 \
  --prompt "<技能目录>/references/prompt.md" -o work/batch_3.txt
```

也可用 `--section "3.2 研究方法"` 按章节名取，或 `--ids 45,46,47` 指定段落。
脚本会自动拼上指令原文，并**拒绝任何非正文 id**（标题、图注、参考文献都会被挡下来）。

2. 读 `work/batch_<n>.txt`，原样送出改写——**不要增删其中任何指令文字**
3. 把模型的回复**原样存成 `work/reply_<n>.txt`**（不要手工摘段落），交给 `apply` 对齐：

```bash
python "<技能目录>/scripts/docx_tool.py" apply work/blocks.json --batch 3 \
  --input work/reply_3.txt -o work/edits.json --progress work/progress.json
```

`apply` 会按空行切分回复，要求**块数与本批段落数完全相等**；不等就报错退出并列出双方数量，**不会写入半成品**。段落之间必须空一行——模型常常把两段并成一段，这正是要拦的情况。

4. 本批自检（见第六节），不合格重跑该批，最多 2 次
5. 全批跑完后确认 `edits.json` 的每个 id 都在 `blocks.json` 里 `kind == "para"` 的段子上
6. `apply` 已自动维护 `work/progress.json`；中断后先跑 `status` 看进度，不要从头再来：

```bash
python "<技能目录>/scripts/docx_tool.py" status work/blocks.json
```

输出会列出每批「完成 / 部分 / 未开始」和下一批的批次号。

**不要手工编辑 `edits.json`。** 它由 `apply` 累积写入，手改最容易把 id 和段落错开一位——那正是本工具要消灭的错误。

`progress.json` 是 `apply` 维护的，格式如下，一般不用手工读写：

```json
{"total_batches": 12, "done": [1,2,3], "failed": [], "updated_at": "..."}
```

### Step 5 回写与自检

```bash
python "<技能目录>/scripts/docx_tool.py" write "论文.docx" work/edits.json -o "论文_降AI版.docx" --diff-md work/对照表.md
python "<技能目录>/scripts/docx_tool.py" check "论文.docx" work/edits.json -o work/check.json
```

`check` 的 verdict 若为 `fail`，先修问题段再重新回写，不要带着已知问题交付。

`write` 内置三道拦截，触到会直接报错退出，**不要用 `--allow-non-para` 绕过去凑合**：

- 输出路径与源文件相同 → 拒绝，绝不覆盖原稿
- 目标 id 不是正文段落（标题 / 图注 / 参考文献 / 公式）→ 列出后全部拒绝回写
- 新文本里夹带了改写指令（含「修改段落」字样）→ 拒绝回写，要求重新生成该批

含超链接的段落默认跳过不改，并列出 id 交用户手工处理。

`write` 打印的 `[跳过]` / `[提示]` / `[警告]` 三类信息必须如实转述给用户，不能吞掉——尤其是「局部格式丢失」和「脚注位置偏移」，用户打开文档后会立刻发现，瞒不住也不该瞒。

### Step 6 交付

给三样东西，并说明：

- `论文_降AI版.docx` —— 改写后的文档
- `work/对照表.md` —— 逐段原/新并列，便于抽检
- 自检摘要 —— 字数、句号、引用标记、数字四项指标

结尾必须加一句：**请用同一个检测器、同一口径复检，不同平台的分数不可横向比较。**

## 五、分批参数

| 参数 | 取值 | 理由 |
|---|---|---|
| 每批字数 | 800–1500，默认 1200 | 超过 1500 模型容易只改开头、后半段照抄 |
| 遇标题 | 强制断批 | 不跨节混改，便于按节核对 |
| 单段超长 | 单独成批，不切段 | 切段会破坏回写（回写以段落为单位） |

## 六、自检指标

| 指标 | 合格线 | 不达标处理 |
|---|---|---|
| 全篇字数变化 | ±10% 内 | 重跑偏离最大的批 |
| 句号数量 | 减少 ≥20% | 重跑该批，强调第 4 条 |
| 逗号数量 | 必须增加 | 重跑该批 |
| 引用标记 `[n]` | 0 丢失 | 立刻修复该段，这是硬伤 |
| 数字 / 百分比 | 0 丢失 | 逐个人工核对；确属「30%」写成「百分之三十」可放过 |
| 「我觉得/我认为」 | 0 残留 | 直接删除 |
| 指令回显 | 0 段 | **fail**，重新生成该批——夹带指令说明模型没在改写 |

脚本会自动算这些并给 `pass / warn / fail`。字数减少、数字出现次数减少，只报 `warn` 不拦交付。

## 七、常见坑

1. **`.doc` 旧格式** —— python-docx 打不开，必须先另存为 `.docx`。
2. **段落 id 错位** —— id 从 0 开始，手抄时容易整体偏移一位。`write` 现在会拒绝回写标题/图注/参考文献，不会真的毁掉标题，但仍会白跑一轮。**一律用 `batch` 取段落、`apply` 写回结果，不要手抄 id，也不要手工编辑 `edits.json`。**
3. **段落内有局部加粗** —— 回写后整段统一为段首 run 的格式，局部强调会丢。脚本会在 write 阶段列出这些段落 id，交付时一并告知用户。
4. **段落含脚注/尾注引用** —— 引用本身会保留，不会丢脚注；但引用在段内的位置可能随语句调整而偏移。交付时提示用户核对这几段。
5. **段落含超链接** —— 脚本默认**跳过不改**（强行改会让链接文字重复）。把 id 列给用户手工处理；确需改写时加 `--force`，改完必须清理重复文字。
6. **报告章节名与正文标题不一致** —— 报告写「3.2 研究方法」，正文写「3.2 研究方法与数据来源」，用模糊匹配，匹配不上让用户点。
7. **改写后字数暴涨** —— 通常是模型自行扩写，重跑该批并强调「不得扩写、不得增加原文没有的信息」。
8. **短文档批次数偏多** —— 遇标题强制断批，800 字的小论文也可能分出 7 批，属正常，不要为了省批次跨节合并。
9. **超过 5 万字的文档** —— 分批数很多。先只跑一节给用户看效果，认可后再继续，避免全量返工。
10. **表格里的文字** —— 不参与改写（`doc.paragraphs` 本身不含表格段落），如果用户要求改表格，需单独处理并说明风险。
11. **页眉、页脚、文本框、脚注正文里的文字** —— 同样不在 `doc.paragraphs` 里，本工具不碰，也不报警。若用户抱怨「摘要里还有 AI 味」，先问清楚那段文字在不在这些位置。
12. **「一、」「（一）」这类手打编号标题** —— 会被认成标题而排除在改写之外（方向安全）。但如果同一篇里正文列表也写成「一、」开头，会一并跳过；此时改用 `--ids` 精确取段。
13. **模型把回复套上代码围栏或编号前缀** —— `apply` 会剥掉 ``` 围栏；编号前缀（「1.」「（1）」）加 `--strip-number` 去掉。段数对不上时会拒绝写入并列出差在哪。

## 八、工具与环境

- 脚本：`scripts/docx_tool.py`，六个子命令：
  `split`（拆文档）/ `batch`（取请求）/ `apply`（写回结果）/ `status`（看进度）/ `write`（生成新 docx）/ `check`（自检）
- 依赖 `python-docx`，缺失时安装：`python -m pip install python-docx`
- 中间文件统一放论文同目录下的 `work/`，不要散落在根目录
- 上手前建议先用 `scripts/make_sample.py` 生成一篇样例论文跑通全流程，熟悉输出格式再上真实稿
- 改动脚本后必须跑回归：仓库根目录 `python -m unittest discover -s tests -v`（21 项，覆盖分类、对齐、拦截、自检）
